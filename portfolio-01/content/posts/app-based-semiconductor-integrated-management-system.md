실제 반도체 공정에서 사용하는 장비의 원격 실시간 제어 및 모니터링을 위한 윈도우 앱 기반 시스템 개발 프로젝트에 참여하였습니다.

실사용자가 있는 서비스에서의 기존 솔루션의 성능 개선과 추가 요구 기능 대응에 대한 개발을 주로 진행하였습니다.

## Project Summary

**Period** : 2025.10 - 2026.08

**Team Size** : 2명

**Tech Stack** : C#, .NET, WPF, HLS, RTSP, VNC

**Description** :
참여한 프로젝트는 반도체 장비의 실시간 스트리밍 및 원격 제어, 녹화 조회 등의 통합 관제 시스템 입니다.

해당 프로젝트는 C#/.NET 기반의 윈도우 데스크탑 앱으로 개발되었습니다. 크게 장비 스트리밍을 위한 미디어 서버, 녹화 파일 서버, 주요 API를 제공하는 마스터 서버, 클라이언트 앱으로 구성되어 있습니다. 

해당 프로젝트는 실제 사용자 환경이 Windows 10, 4 core CPU , 8GB RAM으로 제한된 VDI 환경으로, 클라이언트 환경에서의 성능 최적화가 주요 안건이었습니다.
기존 프로젝트의 경우 아래와 같은 문제점으로 인해 실사용자들의 개선 요청이 있는 상황이었습니다.

- 모든 반도체 장비를 VNC를 통해 영상 스트리밍 시도 -> 클라이언트 앱 및 미디어 서버 네트워크 트래픽 부하, 메모리 부하로 인해 사용 불가 수준
- 모든 CCTV 화면을 원본 해상도 RTSP를 통해 영상 스트리밍 시도 -> 최대 60개 화면을 동시에 올렸을 때, 메모리 사용량 급증 문제
- 기존 클라이언트 프로젝트에서 사용하던 VLCMediaPlayer 라이브러리의 성능 문제 -> 여러 대 동시 RTSP 스트리밍 재생 시 클라이언트 측 CPU 및 메모리 사용량 급증 문제
- 클라이언트에서 녹화 파일 조회 시, 한 시간 분량의 원본 HD 해상도 녹화 파일 다운로드 후 재생 방식 -> 클라이언트 측 네트워크 트래픽 부하

문제 분석 결과, 병목의 핵심은 개별 기능의 오류가 아니라 **원본 품질의 영상 데이터를 제한된 클라이언트 환경에서 그대로 수신, 디코딩, 렌더링하도록 구성된 구조**에 있었습니다. 특히 실사용자는 최대 60개 화면을 동시에 모니터링해야 했기 때문에, 단일 화면 기준으로 동작하던 방식도 다중 화면 환경에서는 CPU, 메모리, 네트워크 부하를 빠르게 증가시키는 원인이 되었습니다.

이에 따라 개선 방향을 단순 성능 튜닝이 아니라, **사용 시나리오별로 필요한 영상 품질과 전송 방식을 분리하는 구조 개선**으로 설정했습니다. 실시간 모니터링 화면은 원본 스트림과 서브 스트림을 분리해 필요한 품질만 선택적으로 수신하도록 변경하고, 클라이언트 디코딩 과정은 직접 제어 가능한 구조로 재설계했습니다. 또한 녹화 파일 조회는 전체 파일 다운로드 방식에서 필요한 구간만 전송하는 스트리밍 방식으로 전환했습니다.

이를 바탕으로 다음과 같이 시스템 아키텍처를 개선했습니다.

- 미디어 서버에서 영상 인코딩 후 RTSP로 원본 스트림/ 서브 스트림 각각 재송출 구조로 변경
- 클라이언트 VLCMediaPlayer 라이브러리를 libavodec 기반 디코딩 파이프라인 직접 설계 구조로 변경
- 녹화 파일 서버를 단순 다운로드가 아닌, HLS 스트리밍 구조로 변경

![IMS 시스템 개념도](/portfolio/semiconductor-management/IMS.png)

- 마스터 파일 서버 : 회원 관리 및 장비 관리 등 전반적인 CRUD API 지원
- 녹화 파일 서버 : 장비 및 CCTV 화면의 녹화 화면 업로드 및 스트리밍 지원
- 모듈 서버(미디어 서버) : 장비 및 CCTV 트랜스 코딩 , 녹화, RTSP 송출 지원
- 클라이언트 앱 : 장비 실시간 모니터링 및 제어, 녹화 조회 등

### Issue 1. 녹화 파일 조회 트래픽 최적화

#### Situation

기존 녹화 파일 서버는 클라이언트가 영상을 조회할 때 1시간 단위의 FHD 녹화 원본 파일 전체를 임시 경로에 다운로드한 뒤 재생하는 구조였습니다.이로 인해 사용자가 짧은 구간만 확인하더라도 GB 단위의 파일이 전송되어 불필요한 네트워크 트래픽이 발생하였습니다.

또한 사용자들은 실제 녹화가 된 시간을 기반으로 원하는 시점을 바로 조회하는 Time Seeking 기능을 요구하였습니다.

#### Task

- 사용자가 원하는 시점의 녹화 영상 조회가 즉시 가능하도록 수정 
- 전체 파일 다운로드를 없애 불필요한 네트워크 트래픽 최적화

#### Action

이를 해결하기 위해 파일 서버의 영상 조회 아키텍처를 단순 다운로드 기반에서 HLS(HTTP Live Streaming) 기반 스트리밍 구조로 재설계하였습니다. 

파일이 업로드 될 때 , 녹화 영상을 일정 길이의 Segment 단위로 분할하고 메타데이터 파일(.m3u8)을 통해 클라이언트가 원하는 시점에 해당하는 Segment만 요청하도록 수정하였습니다.

#### Result

적용 결과, 기존 1시간 단위 파일 전체 다운로드 방식 대비 조회 트래픽을 90% 이상 줄였습니다.
추가로 동시에 탐색 응답성도 개선되었습니다.

### Issue 2. VDI 환경을 고려한 다중 화면 스트리밍 성능 개선

#### Situation

사용자는 클라이언트를 제한된 VDI 환경(Windows 10, 4 core CPU, 8GB RAM)에서 사용중이었습니다.
하지만 기존 시스템의 경우 클라이언트의 리소스 제약을 충분히 고려하지 않은 상태로 개발되어 실제 운영 환경에서 성능 저하와 사용성 문제가 발생하였습니다. 

특히 기존 구조에서는 단일 화면 스트리밍과 다수 화면 스트리밍 모두 별도의 인코딩이나 품질 조정 없이 FHD 해상도의 화면을 RFB 프로토콜로 그대로 전송하고 있었습니다. 이 방식은 단일 장비를 조회할 때에는 큰 문제가 부각되지 않았지만, 다수 장비를 동시에 모니터링하는 환경에서는 클라이언트 CPU 사용량 및 메모리 사용량, 네트워크 트래픽 모두 급격히 증가하는 문제가 발생하였습니다.

#### Task

- 클라이언트 리소스 제약 상황(4Core, 8GB Ram)을 고려하여 성능 최적화
- 최대 60대 화면의 동시 스트리밍 요구 사항

#### Action

단일 화면 스트리밍 조회와 다중 화면 모니터링의 사용 목적이 다르다는 점을 기준으로 스트리밍 정책을 분리하였습니다. 
단일 화면은 사용자가 장비 화면을 상세히 확인하여야 했기에 원본 해상도를 유지하였습니다.
반면 다중 화면의 경우 각 화면이 차지하는 영역이 작기 때문에 해상도와 FPS를 낮춘 서브 스트림을 사용하도록 변경하였습니다.

또한 기존에는 VNC 기반으로 장비 화면의 Raw Pixel을 보내게 되며 클라이언트 및 미디어 서버의 네트워크 트래픽 사용량 등의 리소스 문제가 발생하였습니다. 이를 개선하기 위해 미디어 서버가 반도체 장비의 VNC 서버로부터 화면을 수집한 뒤 원본 해상도와 서브 해상도 스트림을 각각 H.264로 인코딩하고 MediaMTX 오픈소스 라이브러리 RTSP로 전달하는 구조로 재설계하였습니다. 

이를 통해 싱글뷰는 원본 해상도 중심의 고품질 스트리밍을 제공하고 멀티뷰는 낮은 해상도와 FPS를 적용한 경량 스트리밍을 제공하도록 분리하였습니다.

#### Result

Raw pixel 전송 구조를 압축 비디오 스트림 구조로 전환하면서 네트워크 트래픽과 클라이언트 렌더링 부담을 크게 줄였습니다.
VDI 환경에서의 화면 지연과 끊김도 눈에 띄게 개선했습니다.

![멀티뷰 그리드](/portfolio/semiconductor-management/multiview-grid.png)

### Issue 3. 클라이언트 RTSP 디코딩으로 인한 병목 최적화

#### Situation

스트리밍 구조를 최적화한 뒤에는 클라이언트 측 스트리밍 디코딩 처리가 새로운 병목 지점으로 드러났습니다.
기존 클라이언트에서 RTSP 스트리밍 재생을 위해 LibVLC 라이브러리를 사용하고 있었고 초기에는 이를 그대로 재사용하여 다중 화면 스트리밍을 지원하였습니다. 

하지만 스트림 수가 증가할수록 CPU 사용량이 비선형적으로 증가하는 문제가 발생하였습니다. Visual Studio Profiler를 통해 20개 화면을 재생한 상황을 분석한 결과 LibVLC 내부의 네이티브 디코딩 및 렌더링 처리 구간에서 CPU 사용량이 급격히 증가하는 것을 확인했습니다. 특히 WPF 환경에서는 LibVLC가 제공하는 렌더링 경로를 세밀하게 제어하기 어려웠으며 다중 스트림 환경에 맞춰 프레임 처리 및 디코딩 정책, 렌더링 방식을 최적화하는데에는 한계가 있었습니다.

#### Task

- 클라이언트에서 다중 화면 스트리밍 시 발생하는 디코딩 부하, 메모리 사용량 증가 상황 개선

#### Action

LibVLC 기반 재생 구조에서 발생한 CPU 사용량 증가 문제를 분석하던 도중, LibVLC Github 이슈에서도 유사한 다중 스트림 성능 문제가 보고된 것을 확인하였습ㄴ디ㅏ. 이에 따라 범용 플레이어 라이브러리에 의존하는 구조로는 제한된 VDI 환경에 맞춘 최적화가 어렵다고 판단하였고 FFmpeg 기반의 자체 디코딩 파이프라인으로 전환을 진행하였습니다.

새로운 구조에서는 RTSP 스트림 수신 및 패킷 처리, 디코딩, 프레임 전달 과정을 직접 제어할 수 있도록 구성하였습니다. 각 스트림을 독립적으로 처리할 수 있도록 멀티스레드 기반으로 파이프라인을 구성하였습니다. 또한 RTSP 연결 옵션을 조정해 초기 연결 지연을 줄이고자 하였으며 각종 네트워크 예외 상황에서는 자동 재연결이 수행될 수 있도록 수정하였습니다. 

#### Result

그 결과, 60채널 동시 재생 환경에서도 CPU 약 43%, 메모리 500~700MB 수준을 유지했습니다. (4Core GPU, 8RAM 가상머신 테스트 결과)
이후 추가 기능 개발과 스트리밍 상태 추적에도 대응할 수 있는 구조를 확보했습니다.

| 멀티뷰 채널 수 | CPU 사용률 | 메모리 사용량 |
| --- | --- | --- |
| 10채널 | 10~11% | - |
| 20채널 | 14~16% | - |
| 30채널 | 22~23% | - |
| 40채널 | 29~31% | - |
| 50채널 | 35~38% | - |
| 60채널 | 약 43% | 500~700MB |

이를 통해 사용자 환경과 유사한 Windows 10, 4 core CPU, 8GB RAM 조건에서 사용할 수 있는 스트리밍 안정성을 확보했습니다.

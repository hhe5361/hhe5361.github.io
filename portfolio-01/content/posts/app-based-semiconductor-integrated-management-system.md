실제 반도체 공정에서 사용하는 장비들을 원격으로 실시간 제어 및 모니터링하기 위한 윈도우 앱 기반 솔루션 유지보수 프로젝트에 참여하였습니다.

실사용자가 있는 서비스에서 성능 개선과 추가 요구 기능 대응 작업을 약 1년 6개월 정도 진행하였습니다.

## Project Summary

**Period** : 2025.09 - 2026.08

**Team Size** : 2명

**Tech Stack** : C#, .NET, Windows Desktop App, FFmpeg, HLS, RTSP, VNC

**Description** :
장비 단독 스트리밍, 원격 제어, 최대 60대 멀티뷰 모니터링, 녹화 조회, 사용자 간 실시간 채팅을 제공하는 유지보수 프로젝트였습니다.

실제 사용자 환경이 Windows 10, 4 core CPU / 8GB RAM 수준의 제약이 큰 VDI 환경이었기 때문에, 서비스 전반에서 성능 최적화가 주요 안건이었습니다.

## Troubleshooting

### Issue 1. 녹화 파일 조회 트래픽 최적화

#### Situation

기존 녹화 파일 서버는 클라이언트가 영상을 조회할 때마다 1시간 단위의 HD(1080p, 10FPS) 녹화 파일 전체를 임시 경로로 다운로드한 뒤 재생하는 구조였습니다.

짧은 구간만 확인해도 GB 단위 파일이 네트워크를 타면서 내부망 환경에서 조회 성능과 서버 부하 문제가 함께 드러났습니다.

#### Task

전체 파일 다운로드 없이 사용자가 원하는 시점으로 즉시 이동할 수 있도록, 녹화 조회 아키텍처를 바꾸고 전송 트래픽을 줄여야 했습니다.

#### Action

파일 다운로드 기반 조회 구조를 HLS(HTTP Live Streaming) 기반으로 재설계했습니다.

녹화 영상을 Segment 단위로 분할해 필요한 구간만 선택적으로 전송하도록 바꾸고, 클라이언트의 Seek 동작도 전체 파일이 아니라 필요한 Segment만 요청하도록 수정했습니다.

#### Result

불필요한 대용량 다운로드를 제거했고, 기존 1시간 단위 파일 전체 다운로드 방식 대비 조회 트래픽을 90% 이상 줄였습니다.

동시에 탐색 응답성도 개선됐습니다.

### Issue 2. VDI 멀티뷰 스트리밍 병목 현상

#### Situation

제한된 VDI 환경(Windows 10, 4 core CPU, 8GB RAM)에서 TightVNC 기반 화면 전송을 사용하고 있었습니다.

싱글뷰와 멀티뷰 모두 별도 인코딩 없이 1920x1080 / 10FPS 화면을 RFB 프로토콜로 전달하고 있었고, 최대 60대 장비를 동시에 모니터링해야 했기 때문에 클라이언트 CPU, 메모리, 네트워크 부하가 빠르게 치솟았습니다.

#### Task

제한된 자원 환경에서도 안정적으로 장비를 모니터링할 수 있도록 스트리밍 구조를 재설계하고, 네트워크 트래픽과 클라이언트 자원 사용량을 줄여야 했습니다.

#### Action

모듈 서버에서 장비 화면을 수집한 뒤 H.264로 인코딩해 RTSP로 전달하는 구조로 바꿨습니다.

싱글뷰는 원본 해상도 중심, 멀티뷰는 해상도와 FPS를 대폭 낮춘 별도 정책으로 분리해 스트리밍하도록 구성했습니다.

#### Result

Raw pixel 전송 구조를 압축 비디오 스트림 구조로 전환하면서 네트워크 트래픽과 클라이언트 렌더링 부담을 크게 줄였습니다.

VDI 환경에서의 화면 지연과 끊김도 눈에 띄게 개선했습니다.

![멀티뷰 그리드](/portfolio/semiconductor-management/multiview-grid.png)

### Issue 3. 클라이언트 RTSP 디코딩 병목 현상

#### Situation

스트리밍 구조를 최적화한 뒤에도 클라이언트 측 디코딩이 새로운 병목으로 드러났습니다.

GPU가 없는 VDI 환경에서 최대 60채널 멀티뷰를 동시에 띄워야 했고, 기존 LibVLC 기반 재생은 스트림 수가 늘어날수록 CPU 사용량이 비선형적으로 증가했습니다.

내부 디코딩과 렌더링 흐름을 세부적으로 제어하기도 어려웠습니다.

#### Task

다수 스트림 동시 연결 시 발생하는 디코딩 부하, 메모리 사용량 증가, 네트워크 오류 시 재연결 문제를 개선해 멀티뷰 스트리밍을 안정화해야 했습니다.

#### Action

LibVLC 기반 구조를 FFmpeg(Libavcodec) 기반 자체 디코딩 파이프라인으로 전환했습니다.

RTSP 연결 옵션을 조정해 초기 블로킹을 줄였고, `av_read_frame` / `avcodec_send_packet` / `avcodec_receive_frame` 루프로 패킷 처리와 디코딩을 직접 제어했습니다.

AVPacket / AVFrame, SwsContext, 변환 버퍼, ArrayPool을 재사용하고, 비디오 스트림 packet만 선별 디코딩했으며, EOF / Timeout / Connection Reset에 대한 자동 재연결도 넣었습니다.

#### Result

스트림 수 증가에 따른 병목 지점을 코드 레벨에서 직접 제어할 수 있게 됐습니다.

60채널 동시 재생 환경에서도 CPU 약 43%, 메모리 500~700MB 수준을 유지했습니다.

이후 추가 기능 개발과 스트리밍 상태 추적에도 대응할 수 있는 구조를 확보했습니다.

| 멀티뷰 채널 수 | CPU 사용률 | 메모리 사용량 |
| --- | --- | --- |
| 10채널 | 10~11% | - |
| 20채널 | 14~16% | - |
| 30채널 | 22~23% | - |
| 40채널 | 29~31% | - |
| 50채널 | 35~38% | - |
| 60채널 | 약 43% | 500~700MB |

60채널 동시 재생 환경에서도 CPU와 메모리 사용량을 위 수준으로 유지하면서, 사용자 환경과 유사한 Windows 10, 4 core CPU, 8GB RAM 조건에서 사용할 수 있는 스트리밍 안정성을 확보했습니다.
